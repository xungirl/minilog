# minilog benchmarks

Every number in this file comes from a run on this machine. The raw output, including the
exact command line for every run, is in [`results/`](results/). Tables are generated by
`python3 scripts/summarize.py`.

## Environment

| | |
|---|---|
| Date | 2026-11-12 |
| Machine | Apple M2, 8 cores (4 performance + 4 efficiency), 24 GiB RAM, internal SSD |
| OS | macOS 15.4 |
| Java | OpenJDK 21.0.5 (Temurin-21.0.5+11) |
| Broker / controller JVMs | `-Xms512m -Xmx512m -XX:+UseG1GC` (`LocalCluster.JVM_FLAGS`) |
| Benchmark client JVM | `-Xms2g -Xmx2g -XX:+UseG1GC -Dminilog.log=quiet` |
| Topology | 1 controller + 3 brokers, **all separate JVM processes on localhost**, plus the benchmark client in its own JVM |
| Topic | 3 partitions, replication factor 3, `min.insync.replicas=2` (unless stated otherwise) |
| Broker defaults | 64 MiB segments, 4 KiB index interval, no fsync (unless stated), replica fetch long-poll 200 ms |

**Read the numbers with these caveats:**
- There is no network. Loopback hides real network latency and bandwidth limits.
- Three "machines" share 8 cores, one SSD and one page cache.
- Each benchmark run starts a fresh cluster (`Bench` → `LocalCluster`) and deletes its data
  afterwards.
- Runs in the matrix tables last only about 1–4 s each (a warm-up of up to 50,000 messages
  is excluded). The "sustained" tables use 10–25 s windows, and their numbers are lower. The
  sustained numbers are the headline figures.
- "MiB/s" counts payload bytes only (record overhead is 48 B per record plus the key).

All commands are run by `scripts/run-benchmarks.sh`. Every run's command line appears in the
results file just above its `RESULT` line. A single run looks like:

```
java -Xms2g -Xmx2g -XX:+UseG1GC -Dminilog.log=quiet -cp build/libs/minilog.jar \
     dev.minilog.bench.Bench produce --size 1024 --acks -1 --batch 131072 --linger 5 --messages 3000000
```

Observations:
- **Batch size matters most.** For 1 KiB records with acks=all, going from 16 KiB to 128 KiB
  batches raised throughput from about 98 k to about 208 k msgs/s (matrix medians).
- **acks=0 vs acks=1 is a small gap with 100 B records.** The client is the bottleneck: one
  sender thread and synchronous rounds, with one in-flight batch per partition. It is not the
  brokers.
- **acks=all costs about 10–15 % vs acks=1 with 128 KiB batches** (1 KiB: 208 k vs 237 k
  msgs/s), and about 15–17 % with 16 KiB batches. Each acks=all round waits for a follower
  fetch round trip.
- Sustained runs come out lower than the short matrix runs. Segment rolls, a growing page
  cache and more GC work show up over 20 s.

## 3. End-to-end latency

The producer (linger 0) sends at a fixed 5,000 msgs/s with 100 B records. The first 8 bytes
of each value hold `System.nanoTime()` at send time. A consumer in the same JVM records
receive time minus send time. That includes producer batching, replication up to the high
watermark (consumers only see committed records, even with acks=1) and the consumer fetch.
Each run lasts 25 s, and the first 5 s are discarded, leaving about 100,000 samples per run.
3 runs per row. `results/e2e.txt`.

| acks | p50 ms | p99 ms | p99.9 ms | max ms |
|---|---|---|---|---|
| -1 | 0.249 (0.243 – 0.566, n=3) | 0.863 (0.840 – 61.906, n=3) | 2.459 (1.294 – 120.419, n=3) | 17.575 (9.342 – 126.537, n=3) |
| 1 | 0.272 (0.223 – 0.320, n=3) | 1.009 (0.792 – 3.707, n=3) | 4.582 (1.861 – 11.333, n=3) | 18.542 (10.893 – 25.123, n=3) |

The median p50 is about 0.25 ms and the median p99 under about 1 ms. One of the three acks=all
runs had a p99 of 61.9 ms and a max of 126.5 ms; the other two stayed under 1 ms at p99. I did
not find the cause. With 5 JVMs sharing 8 cores, GC pauses or OS scheduling are likely, but this
is unverified. That is why the range is reported, not just the best run.

## 4. fsync policy

Same as the producer test, with 100 k × 1 KiB records, acks=1 and 16 KiB batches. Brokers are
started with different flush settings (`Bench fsync --policy ...`). `results/fsync.txt`.

| policy | acks | msgs/s median (min – max) | MiB/s median (min – max) |
|---|---|---|---|
| every-1 | 1 | 1,934 (1,881 – 1,970, n=3) | 1.9 (1.8 – 1.9, n=3) |
| every-1000 | 1 | 45,028 (42,458 – 48,434, n=3) | 44.0 (41.5 – 47.3, n=3) |
| interval-1000ms | 1 | 94,647 (86,519 – 103,699, n=3) | 92.4 (84.5 – 101.3, n=3) |
| none | 1 | 94,858 (90,316 – 99,822, n=3) | 92.6 (88.2 – 97.5, n=3) |

| policy | broker setting | meaning |
|---|---|---|
| none | (default) | never fsync explicitly; the OS writes back the page cache |
| interval-1000ms | `log.flush.interval.ms=1000` | background fsync of each log every second |
| every-1000 | `log.flush.interval.messages=1000` | fsync whenever 1000 messages have been appended since the last one |
| every-1 | `log.flush.interval.messages=1` | fsync on every append (each append is one producer batch) |

fsync on every append cut throughput about **49×** (94.9 k → 1.9 k msgs/s, medians). A
one-second background fsync cost nothing measurable. This is why minilog (like Kafka) relies on
replication rather than per-message fsync by default. Caveat: on macOS `fsync()` does not force
the drive's write cache (`F_FULLFSYNC` does), and I did not verify which call
`FileChannel.force` uses on this JDK. These numbers are what `force()` cost here, not proof of
power-loss durability.

## 5. Leader failover time

`Bench failover`: a topic with 1 partition and RF=3. One producer sends acks=all records one at
a time, synchronously. The partition leader's JVM is `kill -9`'ed. **Failover time = from the
moment the killed process has exited until the first acknowledgement of a record that was sent
after the kill.** This is the unavailability the client observes: session-timeout detection,
election, metadata propagation over heartbeats, and the client's metadata refresh and retry.
After each kill the broker is restarted and the test waits for a full ISR before the next
iteration. 25 iterations per setting. `results/failover.txt`.

| controller `broker.session.timeout.ms` | iterations | median | p95 | min | max | acked records | acked records lost |
|---|---|---|---|---|---|---|---|
| 1500 ms | 25 | 1574 ms | 1647 ms | 1471 ms | 1672 ms | 113,061 | 0 |
| 500 ms | 25 | 595 ms | 663 ms | 492 ms | 663 ms | 117,771 | 0 |

Failover time is dominated by the session timeout: detection plus about 70–100 ms for
everything else. This is a tunable trade-off. A shorter timeout fails over faster but risks
false failovers during GC pauses.

The first failover run (`results/failover-buggy-clock.txt`) started the clock *before*
`destroyForcibly()`. One iteration reported 0 ms, because the dying leader acked a record in
the few milliseconds before SIGKILL took effect. The clock now starts after the process has
exited. Both settings were re-run, and only the corrected runs are reported.

## 6. Chaos test

`Bench chaos --seconds 120 --seed S`: a topic with 6 partitions and RF=3. Two idempotent
acks=all producers send `p<id>-<seq>` records. A 3-member consumer group (auto-commit every
200 ms) consumes them. Every 2–5 s a random live broker is `kill -9`'ed and restarted after
1–4 s. Halfway through, one consumer is closed and replaced, which forces a rebalance under
chaos. When the run ends, producers stop, the group drains, and the tool checks:

- every acknowledged record was consumed **exactly once** by the group;
- within each partition, each producer's sequence numbers appear in strictly increasing offset
  order.

`results/chaos.txt`

| seed | kills | acked records | consumed records | lost acked | duplicates | order violations | failed sends |
|---|---|---|---|---|---|---|---|
| 20261112 | 17 | 3,393,800 | 3,393,800 | 0 | 0 | 0 | 0 |
| 7 | 16 | 3,087,800 | 3,087,800 | 0 | 0 | 0 | 0 |
| 42 | 19 | 3,152,400 | 3,152,400 | 0 | 0 | 0 | 0 |

Across 3 runs and 52 broker kills, 9,634,000 acknowledged records were all consumed
exactly once, in order. The scope matters here. Brokers were killed; consumers were not.
Consumers are at-least-once by design, so a consumer *crash* would redeliver records since its
last commit. Also, at most one broker was down at a time (the tool waits for a full ISR before
the next kill). With RF=3 and min ISR 2, that is the failure budget the system is designed for.

## 7. Test-suite stability

`./scripts/repeat-tests.sh 10` ran the full suite 10 times in a row with `--rerun-tasks`.
Result: **10/10 runs passed, 55 tests per run, 32–41 s per run**
(`results/test-runs/summary.txt`). After the final client changes (the consumer's in-flight
fetches and the benchmark clock fix), it was run 5 more times: **5/5 passed, 26–27 s per run**.
The suite got faster because consumers no longer wait for idle partitions' long polls.
Across these 15 full runs, no test failed. The last run's `LeaderFailoverIT` output was
`kills=20 acked=14500 consumed=14500 lost=0 duplicated=0`
(`results/test-runs/leader-failover-it-last-run.txt`).
